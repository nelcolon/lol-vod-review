## Q1: Which capture + encoder path gives the lowest overhead with no process injection, and what does it cost in complexity?

### Takeaway
The lowest-overhead path without injection is **Windows.Graphics.Capture (WGC) window capture or DXGI Desktop Duplication (DDA), keeping frames on the GPU as D3D11 textures, into a hardware encoder (NVENC/AMF/QSV)**. FFmpeg now does both captures natively with zero-copy D3D11 output: `ddagrab` for a monitor, and `gfxcapture` (WGC, added in FFmpeg 8.1) for a window or monitor. That makes "spawn FFmpeg" a near-zero-code way onto the same fast path. A custom Rust/C++ pipeline (windows-capture or windows-rs plus Media Foundation or the NVENC SDK) earns its extra complexity only through tighter control of timestamps, ring buffers and per-process audio.

### Cited Findings
**Capture APIs**
- WGC gives you `Direct3D11CaptureFrame` objects with `ContentSize`, `Surface` (a GPU texture) and `SystemRelativeTime`. "The SystemRelativeTime is QPC (QueryPerformanceCounter) time that can be used to synchronize other media elements." — [MS Learn: Screen capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)
- On WGC resize, the frame pool surface keeps the size it was created with. Larger content is clipped and smaller content leaves undefined pixels, so apps should copy the `ContentSize` sub-rect and call `Direct3D11CaptureFramePool.Recreate` to resize. `Recreate` discards pending frames. — [MS Learn: Screen capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)
- WGC HDR: with Windows HD Color on, the content format may not be BGRA8. To avoid washed-out captures, MS recommends `R16G16B16A16_FLOAT` through the whole pipeline, plus tone-mapping to SDR if needed. — [MS Learn: Screen capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)
- WGC yellow border: `GraphicsCaptureSession.IsBorderRequired` arrived in build 10.0.20348 (UniversalApiContract v12), so in practice it needs Windows 11, not Windows 10 19041/19045. Turning the border off requires `GraphicsCaptureAccess.RequestAccessAsync(GraphicsCaptureAccessKind.Borderless)`, which may show a user prompt, and the **`graphicsCaptureWithoutBorder` capability declared in the package manifest**, so the app needs packaging or identity. If the user denies, setting false "will succeed, but the value will be ignored". If another app sets it true for the same window, the border shows. — [MS Learn: IsBorderRequired](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturesession.isborderrequired)
- The FFmpeg `gfxcapture` source (WGC) selects windows by title, class or **exe-name regex** (`window_exe`), by `hwnd`/`hmonitor`, or by `monitor_idx` (`window` = the monitor the window is on). Options include `capture_cursor` (default on), `display_border` (default **off**), `max_framerate` (default 60), and `width`/`height`/`resize_mode` (crop|scale|scale_aspect) for mid-capture size changes. It outputs D3D11 hardware frames. It "does NOT hold a stable FPS" (it delivers at the compositor rate), so add an `fps` filter for CFR. "If the capture source disappears mid-capture (window closed, monitor disconnected), the filter will return EOF." `dup_frames` was added 2026-10-24, so it is post-release master. — [FFmpeg filters.texi (gfxcapture)](https://github.com/FFmpeg/FFmpeg/blob/master/doc/filters.texi); [FFmpeg Changelog: version 8.1 "gfxcapture: Windows.Graphics.Capture based window/monitor capture"](https://github.com/FFmpeg/FFmpeg/blob/master/Changelog); commit history: [vsrc_gfxcapture.c](https://github.com/FFmpeg/FFmpeg/commits/master/libavfilter/vsrc_gfxcapture.c) (added 2025-09-14)
- FFmpeg `ddagrab` (DDA) "exclusively returns D3D11 Hardware Frames, for on-gpu encoding". Options: `output_idx`, `draw_mouse` (hardware cursor only; game-drawn cursors are always captured), `framerate` (**default 30**, so set 60), `video_size`/`offset_x`/`offset_y` cropping, `output_fmt` (bgra, or `x2bgr10` for 10-bit/HDR, which fails if unavailable), and `dup_frames` (default true, duplicates frames to keep near-constant rate). "There is no background buffering going on", so if the filter is polled too slowly the frame interval grows. Canonical zero-copy example: `ffmpeg -f lavfi -i ddagrab -c:v h264_nvenc -cq 18 output.mp4`. — [FFmpeg filters.texi (ddagrab)](https://github.com/FFmpeg/FFmpeg/blob/master/doc/filters.texi)
- DDA (`IDXGIOutput1::DuplicateOutput`): the D3D device "must be created from the adapter to which the output is connected", which is the hybrid-laptop trap: the iGPU often owns the panel while the game renders on the dGPU. `DXGI_ERROR_UNSUPPORTED` covers unsupported desktop modes (retry after `EVENT_SYSTEM_DESKTOPSWITCH`/`WM_DISPLAYCHANGE`). `E_ACCESSDENIED` covers the secure desktop (UAC/lock), which needs LOCAL_SYSTEM. **By default at most four processes** can duplicate at once (`DXGI_ERROR_NOT_CURRENTLY_AVAILABLE`). MS says to prefer `DuplicateOutput1` for performance. Monitor-only, one output per interface. — [MS Learn: DuplicateOutput](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput)
- DDA always hands out `B8G8R8A8_UNORM` (with DuplicateOutput) and dirty/move rects. The pointer may be separate: if hardware overlays the cursor, the app must draw it from `GetFramePointerShape`. `AcquireNextFrame` returns `DXGI_ERROR_ACCESS_LOST`, which must be handled by recreating duplication. — [MS Learn: Desktop Duplication API](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api)
- OBS Window Capture "Automatic" chooses between BitBlt and WGC by window class and falls back to BitBlt when WGC is unsupported. OBS game capture (graphics-hook) has per-API hook DLLs (d3d8/9/10/11/12, dxgi, gl, vulkan), an injector helper, and an "anti-cheat compatibility hook" mode that injects by thread ID. — [OBS window-capture.c](https://github.com/obsproject/obs-studio/blob/master/plugins/win-capture/window-capture.c); [OBS game-capture.c](https://github.com/obsproject/obs-studio/blob/master/plugins/win-capture/game-capture.c); [graphics-hook dir](https://github.com/obsproject/obs-studio/tree/master/plugins/win-capture/graphics-hook)
- OBS's own compatibility list marks **`LeagueClientUx.exe` (the League client/launcher) as blocked for Game Capture**: "League of Legends Launcher cannot be captured using Game Capture. Use Window Capture or Display Capture instead." The in-game process has no entry in the 51-entry list. — [OBS compatibility.json](https://github.com/obsproject/obs-studio/blob/master/plugins/win-capture/data/compatibility.json)

**How League renders now**
- Riot's current system requirements say League on Windows **requires DirectX 11 (feature level 11_0)**. The DX11 requirement was announced in Patch 25.02, and since 25.21 the Play button is greyed out on hardware that does not meet it. Minimum OS is **Windows 10 build 19041+ or Windows 11 with TPM 2.0** (the Vanguard "VAN 9004" error on older builds). Retail editions only. — [Riot Support: LoL minimum & recommended requirements](https://support.riotgames.com/en-us/league-of-legends/performance/minimum-and-recommended-system-requirements-league-of-legends)
- The task prompt says "DX11 since 2023 patch". I could not verify that date this session: Riot's page frames the DX11 *requirement* around patch 25.02 and 25.21. Earlier DX11 availability or default status is unconfirmed (see Gaps).

**Encoders**
- NVENC on GeForce: "the number of concurrent encode sessions is limited to **8 per system**" for non-qualified (consumer) cards. Codecs: H.264 on all generations; HEVC 8-bit from 2nd-gen Maxwell; HEVC 10-bit from Pascal; **AV1 encode only on Ada (RTX 40) and Blackwell (RTX 50)**. Some chips (e.g. GP104, AD104) have 2-3 NVENC engines. — [NVIDIA NVENC Application Note, SDK 13.0](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-application-note/index.html)
- NVIDIA per-engine 1080p throughput (SDK 13.0, Windows 11), **H.264 P5 VBR HQ: Turing 264 fps, Ampere 266, Ada 283, Blackwell 317**; P7 HQ is about 207-227 fps; P1 is about 830-950 fps. HEVC P5 HQ: Ada 411, Blackwell 521. AV1 P5 HQ: Ada 440, Blackwell 552. So 1080p60 uses roughly 20-25% of one engine at P5 and about 6-7% at P1. — [NVIDIA NVENC Application Note](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-application-note/index.html)
- The FFmpeg 9.0 Changelog says "Remove deprecated NVENC options and support for pre-11.1 SDK versions", which implies a minimum driver requirement for newer FFmpeg builds. FFmpeg 9.x also adds AMF features and memory mapping, and 8.1 added a D3D12 H.264 encoder. — [FFmpeg Changelog](https://github.com/FFmpeg/FFmpeg/blob/master/Changelog)
- ScreenRecorderLib is a .NET library that uses **native Media Foundation for realtime H.264** (MF picks the GPU's hardware MFT). It needs the Media Feature Pack on Windows N/KN editions and the VC++ redistributable. — [ScreenRecorderLib README](https://github.com/sskodje/ScreenRecorderLib)
- windows-capture 2.0.1 (Rust and Python) supports WGC **and DXGI Desktop Duplication**, with a "hardware-accelerated" built-in encoder (Media Foundation based; the README example writes `video.mp4`) and "monotonic audio timing". Settings include cursor capture, draw-border, dirty-region, minimum update interval and secondary windows. MIT licensed. — [windows-capture README](https://github.com/NiiightmareXD/windows-capture)

### Inferences
- **Ranking by overhead (no injection):** FFmpeg `gfxcapture`/`ddagrab` into `h264_nvenc`/`hevc_nvenc`/`av1_nvenc` (or `*_amf`/`*_qsv`) with D3D11 frames kept on the GPU is about as cheap as an off-the-shelf path gets. The capture costs a compositor copy plus an NVENC session at a small slice of one engine. Any path that does `hwdownload`/CPU readback (GDI BitBlt, `gdigrab`, `ddagrab,hwdownload` into x264) adds a 1080p/1440p BGRA copy per frame (about 8-15 MB per frame at 60 fps) plus CPU encode, and competes with League, which is CPU-bound.
- **BitBlt/gdigrab: why not.** It reads through GDI into system memory, so CPU copies at every frame. It often gets black or stale frames from DirectX flip-model swapchains. It cannot do zero-copy to a hardware encoder. (Inference from the API design; the OBS source shows BitBlt survives only as a fallback when WGC is unsupported.)
- **Game-hook injection (OBS graphics-hook)** is the only path that captures true exclusive fullscreen at the game's own present rate. However, League runs Riot Vanguard, a kernel anti-cheat (implied by Riot's VAN error codes and TPM 2.0 requirement). Shipping your own injector is a non-starter. Even OBS's signed hook is an anti-cheat gamble that Riot controls. Recommend **no injection**.
- **WGC window vs DDA monitor for League.** WGC window capture via exe match (`League of Legends.exe`) records only the game, follows it across monitors, and excludes overlays and notifications. DDA records the whole monitor, including Discord popups and the alt-tabbed desktop. WGC needs Win10 1903+ for HWND capture from desktop apps (from memory, see Gaps), which League's 19041 minimum already guarantees. DDA's single-adapter rule makes it fragile on hybrid laptops (see Q3).
- **Complexity ladder.** FFmpeg CLI child process takes days. Rust windows-capture with its MF encoder takes about 1-2 weeks. Custom WGC plus the NVENC SDK, AMF and QSV with your own muxer and ring buffer takes weeks to months, mostly in vendor fallback, device-lost and resize handling.
- **Typical CPU cost of x264 at 1080p60** (veryfast is often cited as 1-3 cores of load) is not verified here. Treat x264 as an emergency fallback only.

## Q2: Is driving the user's OBS via obs-websocket a viable MVP path, and what are its limits for frame-accurate timestamps?

### Takeaway
Yes, as an MVP or "power user" mode. obs-websocket v5 ships inside OBS (28+). It exposes start/stop record with the output path, replay-buffer save with the saved path, file split, chapter markers and stats. But it gives no per-frame wall-clock timestamps: only a millisecond `outputDuration`/timecode polled over a socket. Event-to-video mapping is therefore approximate, likely within tens of ms, and it depends on the user's scene, encoder and output configuration, which you do not control.

### Cited Findings
- Requests (all "Added in v5.0.0" unless noted): `StartRecord`; `StopRecord` returns **`outputPath`**; `GetRecordStatus` returns `outputActive`, `outputPaused`, `outputTimecode` (formatted string) and **`outputDuration` (milliseconds)**, plus `outputBytes`; `StartReplayBuffer`; `SaveReplayBuffer`; `GetLastReplayBufferReplay` returns **`savedReplayPath`**; `SplitRecordFile` (v5.5.0); `CreateRecordChapter` (v5.5.0; "As of OBS 30.2.0, the only file format supporting this feature is Hybrid MP4"). — [obs-websocket protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)
- Events: `RecordStateChanged` (`outputActive`, `outputState`, and `outputPath` once stopped); `RecordFileChanged` (`newOutputPath`, v5.5.0, fires on split); `ReplayBufferSaved` (`savedReplayPath`); `ReplayBufferStateChanged`. `GetStats` gives `activeFps`, `renderSkippedFrames`, `outputSkippedFrames`, `outputTotalFrames`, `availableDiskSpace` and so on. The handshake negotiates `rpcVersion`, with optional auth. — [obs-websocket protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)
- OBS 30.2.0 (2024-07-12) added **Hybrid MP4** (beta): it "combines fault-tolerance of fragmented MP4 with wide compatibility and faster access times of regular MP4" and "supports inserting chapter markers via a hotkey or API". — [OBS 30.2.0 release](https://github.com/obsproject/obs-studio/releases/tag/30.2.0); [OBS KB Hybrid MP4](https://obsproject.com/kb/hybrid-mp4)
- OBS 33.0 (2026-10-23) changed Safe Mode so it **does not start the WebSocket server**, which means your integration silently breaks if the user launches OBS in Safe Mode. It also "Improved file splitting for Hybrid MP4/MOV". — [OBS 33.0.0 release](https://github.com/obsproject/obs-studio/releases/tag/33.0.0)
- OBS Game Capture is blocked for the League client (`LeagueClientUx.exe`); OBS points users to Window or Display Capture. — [OBS compatibility.json](https://github.com/obsproject/obs-studio/blob/master/plugins/win-capture/data/compatibility.json)

### Inferences
- **Timestamp strategy with OBS:** record `T0 = QPC/wall-clock` when `RecordStateChanged(outputState=OBS_WEBSOCKET_OUTPUT_STARTED)` arrives. Then periodically sample `GetRecordStatus.outputDuration` against local wall-clock to fit an offset and drift line. Error sources include websocket latency, the gap between OBS's internal start and the first encoded frame, encoder delay and B-frames. A practical MVP check is to `CreateRecordChapter` at each detected game event (Hybrid MP4 only). The chapter is then embedded in OBS's own timeline, so no drift fitting is needed.
- **Limits:** a hard dependency on the user installing OBS, enabling the WebSocket server and sharing the password; you must create or require a scene with a League window source. OBS's encoder, bitrate, container and paths are set by the user. Replay-buffer length is set in OBS output settings, not via a simple request (you can probably change it through profile parameter requests; not verified). And it is GPL-free, since you only talk over a socket.
- **Embedding libobs / obs-studio-node instead** puts you under GPL-2.0 (both repos are GPL-2.0). Linking libobs into a closed-source app is not viable. Running it as a separate process that you control over IPC is a gray area that needs legal review. Streamlabs Desktop is open-source GPL for this reason.

### Gaps
- No measured latency or accuracy figures for obs-websocket record-start or `outputDuration` vs actual frame PTS.
- I did not verify whether obs-websocket v5 can set replay-buffer duration directly.

## Q3: What are the pitfalls of WGC with League specifically (fullscreen exclusive, alt-tab, resolution changes, window handle changes between client and game)?

### Takeaway
League has two distinct processes and windows: the Electron/CEF client `LeagueClientUx.exe` and the game `League of Legends.exe`. A recorder must wait for the game window to appear, bind to it, handle the size it starts at, and stop on window close (gfxcapture returns EOF). WGC copes with borderless and windowed modes well. Exclusive fullscreen and alt-tab or minimize can produce stalls or no frames, so recommend borderless mode and design for frame gaps.

### Cited Findings
- FFmpeg gfxcapture: when the window closes, the filter returns EOF. Frames arrive only at the compositor rate, so a static or minimized source "may not deliver any frames at all", which also stalls the fps filter unless `dup_frames` is used. Canvas width/height lock to the *initial* source size unless forced, with `resize_mode` crop (default), scale or scale_aspect. — [FFmpeg filters.texi (gfxcapture)](https://github.com/FFmpeg/FFmpeg/blob/master/doc/filters.texi)
- WGC native: a resize requires `Recreate`, and content larger than the pool is clipped. — [MS Learn: Screen capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)
- WGC border removal needs Windows 11 (build 20348+ API) plus a manifest capability and user consent. On Windows 10 19041-19045, the yellow border cannot be removed via `IsBorderRequired`. — [MS Learn: IsBorderRequired](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturesession.isborderrequired). Note that FFmpeg gfxcapture defaults `display_border` to off, so its exact mechanism on Windows 10 is unclear (Gap).
- The League client is unsupported by OBS game capture, so window or display capture is the OBS-recommended route. — [OBS compatibility.json](https://github.com/obsproject/obs-studio/blob/master/plugins/win-capture/data/compatibility.json)
- DDA alternative: `ACCESS_LOST` on mode changes and fullscreen transitions, `UNSUPPORTED` in some desktop modes, a device that must belong to the adapter owning the output (hybrid laptops), and a limit of four duplicating processes. — [MS Learn: DuplicateOutput](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput); [MS Learn: Desktop Duplication API](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api)

### Inferences
- **HWND lifecycle:** poll `EnumWindows` or use `SetWinEventHook(EVENT_OBJECT_CREATE/SHOW)` for the `League of Legends.exe` window (class name believed to be "RiotWindowClass"; not verified). Start capture once the window is visible and sized, and correlate with the Live Client Data API (port 2999) becoming available. Treat window destroy or EOF as end of game. Reconnects create a new process and HWND, so segment the recording per HWND.
- **Fullscreen exclusive:** with DX11 flip-model and Windows' fullscreen optimizations, "fullscreen" in modern games is usually composed by DWM, and WGC/DDA then work. Truly exclusive or independent-flip presentation can bypass the composition path that WGC/DDA see, causing black or frozen frames or `ACCESS_LOST`. Advise users to use League's Borderless mode, and detect frozen output by checking for no new frames for N ms. Not verified with League this session.
- **Alt-tab/minimize:** minimized windows produce no WGC frames. For VOD review it is better to emit duplicates or black (`dup_frames`) than to stall, so the timeline stays aligned with wall-clock.
- **Resolution changes mid-game:** fix the output canvas, e.g. scale_aspect to the start resolution, rather than restarting the encoder. MP4 and most H.264 streams do not tolerate mid-stream size changes cleanly.
- **HDR monitors:** capture into FP16 or 10-bit and tone-map, or force SDR (OBS has a "force SDR" WGC option), or videos look washed out.
- **Hybrid laptops:** WGC is generally more robust than DDA across adapters, but encode on the GPU that owns the captured texture, or add a cross-adapter copy cost.

### Gaps
- No League-specific WGC bug reports or forum threads gathered (search unavailable). Black-screen behaviour in League's "Fullscreen" mode should be tested on real hardware.
- The League game window class and title are not verified from a primary source.

## Q4: What's the best practice for crash-safe long recordings?

### Takeaway
Never write a plain `moov`-at-end MP4 for a 20-45 minute recording. Use **MKV**, **fragmented MP4**, or **Hybrid MP4** (OBS 30.2+), or write MPEG-TS/MKV and remux to faststart MP4 after the game. Pair that with a short, fixed keyframe interval (1-2 s) so clip cuts and seeks are precise. Use H.264 as the playback-safe codec in Chromium/WebView2. Only use HEVC/AV1 after checking decode support.

### Cited Findings
- OBS describes Hybrid MP4 as combining fragmented-MP4 fault tolerance with regular-MP4 compatibility and access speed. OBS beta builds switched their default container from fragmented MP4 to Hybrid MP4. — [OBS 30.2.0 release notes](https://github.com/obsproject/obs-studio/releases/tag/30.2.0)
- HEVC in Chromium on Windows: hardware decode has been on by default since **Chrome 107**, via D3D11VideoDecoder and **without** extra installs. **Edge uses the Media Foundation MFT and "need[s] to install HEVC Video Extension"**. Electron 22+ includes Windows HEVC hardware decode. There is no software fallback in Chrome. GPU floor: NVIDIA GTX 645+, AMD RX 460+, Intel HD 4400/515+. — [StaZhu/enable-chromium-hevc-hardware-decoding](https://github.com/StaZhu/enable-chromium-hevc-hardware-decoding)
- NVENC AV1 encode is limited to RTX 40/50, and HEVC 10-bit needs Pascal or newer. — [NVIDIA NVENC App Note](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-application-note/index.html)
- OBS 28 (2022-09-01) added HDR and 10-bit only via HEVC and AV1. — [OBS 28.0.0 release](https://github.com/obsproject/obs-studio/releases/tag/28.0.0)

### Inferences
- **Container recipe for a custom or FFmpeg path:** record with `-f matroska`, or `-movflags +frag_keyframe+empty_moov+default_base_moof` for fMP4. After the game, run `ffmpeg -i in.mkv -c copy -movflags +faststart out.mp4` (seconds for a 30-minute file). If you use MKV, kill FFmpeg gracefully (send `q` on stdin), not with `TerminateProcess`, so it finalizes cues. MKV without cues stays playable but seeks slowly.
- **WebView2 is Edge-based**, so HEVC playback may need HEVC Video Extensions (paid in the Store on many SKUs). That is an inference from the Edge behaviour above, not verified for WebView2 specifically. Electron (Chromium) avoids this. H.264 High at 1080p/1440p is the safe default. AV1 is an option for RTX 40/50 and RDNA3 users where the playback stack has AV1 hardware decode (AV1 decode support is not verified here).
- **Keyframe interval:** a 1 s GOP (`-g 60` at 60 fps; NVENC `-forced-idr 1` where needed) lets `-ss/-to` stream-copy cuts land within 1 s. With B-frames off or low (`-bf 0`/`-bf 2`), stream-copy cuts are cleaner. File size cost vs a 2-4 s GOP is modest at 10-20 Mbps (estimate, unmeasured).
- **CFR vs VFR:** WGC and gfxcapture are VFR by nature. Either force CFR with `fps=60` (duplicating or dropping frames) so frame index × 1/60 = time, or keep VFR but preserve true PTS from QPC. Browser `<video>` seeking uses PTS, so VFR with correct PTS is accurate. Trouble comes from VFR with wrong or reset timestamps.
- **Storage:** bitrate (Mbps) × 1800 s / 8 = MB per 30 minutes. That gives 10 Mbps ≈ 2.25 GB, 15 Mbps ≈ 3.4 GB, 20 Mbps ≈ 4.5 GB; a 45-minute game at 20 Mbps ≈ 6.75 GB. Lower for HEVC/AV1 at equal quality. Use CQ/VBR with a cap (NVENC `-rc vbr -cq 23 -maxrate 20M`) rather than raw CBR. Implement quota-based auto-cleanup (keep last N games, or under X GB, while pinning clips) and check free disk space before starting. Sustained writes of 1-3 MB/s are trivial for SSD endurance: about 4.5 GB per game means 100 games is about 0.45 TB written, well under typical TBW ratings.

### Gaps
- No primary source fetched for MF's fragmented-MP4 sink options, or for `ffmpeg -ss` keyframe semantics (from documented FFmpeg behaviour: `-ss` before `-i` with `-c copy` snaps to the preceding keyframe).
- AV1 hardware decode support in Chromium/WebView2 on Windows was not verified.

## Supplementary: audio, A/V sync, replay buffer and timestamping (cross-cutting findings)

### Takeaway
Use WASAPI **process loopback** to capture only the League game process tree, plus a separate mic track, muxed as multi-track MKV/MP4. Timestamp everything (video frames, audio packets, polled game events) on the **QPC** clock, which WGC and DDA already report. For clips, prefer "record the whole game, then cut with stream copy at 1 s keyframes". Use an in-RAM ring of encoded packets only if you need clips without full recordings.

### Cited Findings
- Process loopback: `ActivateAudioInterfaceAsync` with a new activation structure captures audio "only from the specified process, and its children" (include tree) or everything *except* that tree (exclude tree). It is endpoint-independent, and a process that renders no audio gives silence. Microsoft's sample states that "this sample requires **Windows 10 build 20348** or later." — [MS Learn: Application loopback audio sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)
- OBS 28.0 (2022-09) "Added application audio capture on Windows to allow capturing the audio output from a single process", which is the same API in production use. — [OBS 28.0.0 release](https://github.com/obsproject/obs-studio/releases/tag/28.0.0). Conflict: OBS and the community widely state it works on Windows 10 2004 (19041), but MS's sample says 20348. I did not verify the exact build gate this session. Test on 19045.
- WGC `SystemRelativeTime` is QPC time intended for syncing other media. — [MS Learn: Screen capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)
- windows-capture 2.0 advertises "monotonic audio timing" in its encoder. — [windows-capture README](https://github.com/NiiightmareXD/windows-capture)
- `ddagrab` duplicates frames when the desktop is idle (`dup_frames`), but has no background buffering, so a stalled consumer stretches intervals. — [FFmpeg filters.texi](https://github.com/FFmpeg/FFmpeg/blob/master/doc/filters.texi)
- OBS replay buffer is saved via websocket `SaveReplayBuffer`, and `ReplayBufferSaved` returns the path. — [obs-websocket protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)

### Inferences
- **Timestamp mapping:** keep a session clock as `QPC at first video frame = PTS 0`. Each video frame's PTS is `(SystemRelativeTime − T0)`, and each audio buffer's PTS comes from its QPC position (`IAudioCaptureClient::GetBuffer` returns a QPC position). Stamp each Live Client Data API poll with QPC before and after the request, using the midpoint. League's `eventTime` is in game-seconds, so fit `gameTime → QPC` by linear regression over polls of `/liveclientdata/gamestats` `gameTime`. Then event video time = `QPC(eventTime) − T0`. With PTS-preserving muxing, dropped frames do not shift later frames. Log drops (gaps > 1.5 frame intervals) to a sidecar JSON.
- **FFmpeg CLI timestamping:** you cannot get per-frame QPC out of the ffmpeg CLI easily. Use `-copyts`, or parse stderr `-progress`, or record your own QPC at process start and the first-frame time (e.g. from `-stats_period`). That gives an approximate offset in the tens of ms, similar to OBS. A custom pipeline in Rust or C++ is the way to frame-accurate mapping.
- **Ring buffer design:** keep encoded H.264/HEVC packets, not raw frames, in a deque bounded by duration, starting at a keyframe. At 15 Mbps, 60 s is about 112 MB of RAM, which is fine. On save, flush from the first keyframe ≤ (event − pre-roll), keep appending for post-roll, then mux. Alternatively record the full game to disk and cut clips afterwards with `ffmpeg -ss A -to B -c copy` (instant, keyframe-snapped) or re-encode (frame-exact, seconds of GPU time). For a VOD-review tool that records full games anyway, cutting from the full recording is simpler and removes a second encoder session.
- **Multi-track:** write track 1 as game audio (process loopback), track 2 as mic, and optionally track 3 as the system mix. MKV handles this natively and MP4 supports multiple AAC/Opus tracks. Browsers play only the first or default audio track, so for in-app playback either pre-mix or use Web Audio with separate files.
